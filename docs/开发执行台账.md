# 编剧助手 · 开发执行台账

> 本文件是「编剧助手」Flutter 工程的**协调总控**：记录工作包拆分、阶段门禁、关键决策与环境约束。
> 需求规格以仓库根目录 `README.md`（开发文档，共 22 章）为唯一权威来源，本台账不重复需求，只记录**怎么执行、执行到哪、为什么这么定**。

---

## 一、执行模式

- **协调方式**：单协调者 + 工作包（WP）串行推进，每个 WP 独立可验证、可回滚。
- **开发方法**：核心逻辑（计算、规则、存储、导出）采用测试先行——先写失败测试并确认失败原因，再写最小实现使其通过，最后重构，全程保持回归绿。UI 层以 Widget 测试与快照测试兜底。
- **推进节奏**：只有通过当前阶段门禁（Gate）才进入下一阶段；门禁不通过时在该 WP 内修复，不跨阶段带病推进。
- **检查点纪律**：每完成一个 WP 且测试全绿，立即 commit 并 push。原因是执行环境不稳定（见第四章第 2 条），只有远端副本才是安全的。
- **状态标记**：`待开始` / `进行中` / `已完成` / `受阻`。

## 四、关键决策与约束（含理由）

1. **需求规格不在本台账重述**：`README.md` 已是完备设计文档（数据模型、目录结构、模块职责、导出规则、验收 Checklist 齐全），本台账只做执行编排，避免双份规格漂移。
2. **执行环境不稳定，一切以远端为准**：
   - 容器根文件系统（`/`、`/opt`、`/tmp`、`/root`）会在会话间重置，2026-10-13 已实际发生一次，导致首次安装的 SDK 与已写入工作区的两个文件全部丢失；
   - 更严重的是工作区所在的 OSS 挂载（fuse）在执行中掉线且进程消失，容器内无法自行恢复，整个持久工作区在当次会话不可达；
   - 因此确立两条规则：**开发目录放本地盘**（`/root/work/bianju`，IO 快且不受 fuse 影响），**每个 WP 完成即 commit + push**，以 GitHub 远端为唯一可信副本。
3. **工具链可复现**：Flutter SDK 安装包缓存在持久目录 `.toolchain/` 下，`scripts/bootstrap_env.sh` 幂等恢复（命中缓存约 1 分钟，未命中需下载 1.5GB）。版本号固定在脚本内，避免不同会话拿到不同 SDK。
4. **本机可验证的构建目标只有 Web**：iOS 构建需 macOS + Xcode，Windows 构建需 Windows + Visual Studio，本机（Linux）两者都不具备，Linux 桌面工具链（clang++/cmake/ninja）也缺失。因此
   - 本机用 `flutter build web --release` 作为「构建链路无阻断」的代理验证（G3）；
   - 真正的 iOS 未签名 IPA 与 Windows Release 由 GitHub Actions 出包（G4），与开发文档第 20 章一致；
   - 工程额外保留 `web/` 平台目录仅服务于本机验证，不属于文档规定的交付平台。
5. **状态管理选 Provider**：撤销重做、自动保存、角色库与分镜引用联动都需要跨页共享状态，与文档第 19 章一致，不引入更重的方案。
6. **凭据不落盘**：推送用的访问令牌只在推送命令执行时注入，不写入 `.git/config`、脚本或任何仓库文件；仓库内不出现任何令牌。
7. **时长计算的「吸收位」约定**：所有自动补齐与四舍五入误差都由「最后一个启用且未锁定」的分镜承担；若补齐会让它低于 1 秒，则拒绝该次修改（返回原列表）并交由校验中心报错。这样既守住「启用分镜之和 = 总时长」的不变量，又不会静默产生非法时长。
8. **导出严格「有内容才输出」**：空字段不输出 `null`、不输出「未填写」、不输出空行（文档 17.2），由导出快照测试锁定该行为，防止后续重构回归。
9. **服务层一律纯函数式**：`character_service` / `template_service` / `custom_options_service` / `export_service` 都接收 `Project` 返回新的 `Project`，不持有可变状态。这样撤销重做只需按快照记录，跨页共享状态也只在 Provider 层出现一次。
10. **一致性检查是启发式的，级别封顶为警告**：服装、外貌、道具、光线、时间等维度都靠关键词与词表匹配，做不到语义级理解。为避免误报阻断创作，这些冲突最高只到「警告」，在统一校验中心折算为「提示」，并提供忽略/确认入口（文档 10.2）。
11. **v1→v2 迁移的取舍**：文档 16.5 同时写了「尝试按名称匹配自动补建 Character 档案」与「匹配不到则保留为自定义兜底」，两者存在张力。实现按「有名则补建档案并回填引用、名字为空才留作自定义兜底」处理，理由是这样最大限度保住引用关系，且不会凭空造出无名角色。
12. **导出字段顺序固定**：时长 → 节奏 → 时间标记 → 主体动作 → 动作流程 → 镜头运动 → 镜头补充 → 背景变化 → 光线氛围 → 保持特征 → 台词角色 → 台词 → 环境音 → 背景音乐。文档 17.5 的示例中两个分镜字段顺序不一致（示例只展示已填字段），这里取 UI 字段顺序（文档 3.5）作为统一顺序，并由导出快照测试锁定。
13. **对文档缺口的处理**：文档 16.1 的 `Project` 引用了 `ConsistencyRules` 但未定义，按 10.1 的八个检查维度补齐为八个开关，并与 `ConsistencyIssue` 同文件维护，以保持第十八章 models/ 六文件的目录结构不变。
